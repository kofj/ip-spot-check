# Stage 路线图

**最后更新**：2026-10-31
**当前 Stage**：Stage 0
**总体进度**：0%

---

## 愿景

把多家 IP 数据源的结论并列呈现，不合并成总分，让用户看到证据链而不是一个无法验证的数字。

---

## 排序原则

**按风险从高到低排，不按依赖从底到顶排。**

项目最大的风险不是技术实现，而是「多源并列这件事有没有人需要」。所以 Stage 1 直接验证核心假设——用一个最粗糙的脚本，把几个源的结论并排打出来，发给目标用户看。如果这个假设不成立，后面所有工程都是浪费。

技术的风险次之：cache 策略决定免费额度能撑多大，这个必须在架构定型前验证。

### Stage 1：分歧验证

**状态**：规划中
**目标**：用最少的代码验证"多源分歧真实存在且足够高频"

**核心假设**：
- H1：同一 IP 在多个源（或多家检测站）的结论经常互相矛盾，且这个矛盾对目标用户有意义

**做法**：写一个一次性脚本（可以不进仓库，或进 `cmd/probe`），对一个 IP 列表并行拉取 4–6 个源，并排打印。重点不是代码质量，是**看结果**。

**验收**：
- [ ] 拿到 50 个以上 IP（自己的 VPS / 代理 / 家宽 / 公共 DNS / 已知机房）的并列结论
- [ ] 统计出"源之间不一致"的比例
- [ ] 至少找到 3 个"不同检测站给出的结论明显打架"的具体案例
- [ ] 把案例发给 2 个以上目标用户（跨境 / 运维），收到真实反应

**回滚**：无需回滚，脚本删掉即可
**已知局限**：脚本不追求工程质量，会有硬编码 IP、无错误处理

**对后续 Stage 的影响**：
- 如果 H1 不成立（分歧罕见或用户不关心）→ **整个项目应该停在这里**，这是这个 Stage 存在的意义
- 如果成立 → 分歧的具体形态决定 Stage 4 的展示设计

---

### Stage 2：源 adapter 与采集骨架

**状态**：规划中
**目标**：把 Stage 1 的脚本重构为可维护的 adapter 结构

**核心假设**：
- H2：6 个免费源（Team Cymru ASN、RDAP、MaxMind GeoLite2、Spamhaus、AbuseIPDB、PTR）足以构成有意义的画像

**范围**：
- 每个源一个 adapter，统一接口：`Query(ip) (Observation, error)`
- adapter 独立超时与降级，单源失败不影响整体
- 原始观测入库（SQLite），不存结论
- 不需要 HTTP 服务，先用 CLI 驱动

**验收**：
- [ ] 6 个 adapter 全部可跑，各自有单元测试
- [ ] 单源故障时整体仍返回，失败字段明确标记
- [ ] 原始观测表结构支持"同一 IP 多时点"查询

**非目标**：不做缓存、不做 Web、不做并发优化

**对后续 Stage 的影响**：adapter 接口一旦定型，Stage 3 的编排才好写

---

### Stage 3：查询编排与缓存

**状态**：规划中
**目标**：并发编排 + 三层缓存（边缘 1h / origin 24h / 历史表），把源消耗压到免费额度内
**详细设计**：[stage-3.md](stage-3.md)

**核心假设**：
- H3：三层缓存能把源 API 消耗压到日额度以内，且可观测

**必须实现**：
- Singleflight 合并同 IP 并发，防缓存击穿烧额度
- 每源配额守卫，计数持久化到 DB，超限时如实显示"额度耗尽"
- 命中率、源调用次数、singleflight shared 比例埋点（`/metrics`）
- 缓存与配额走接口抽象（单机只是一种实现，为多副本留路）

**验收**：
- [ ] 首次查询 P95 < 3s，缓存命中 P95 < 100ms
- [ ] 同 IP 并发 50 请求，源只被调用 1 次
- [ ] 灰度 24 小时，统计出真实命中率与各源消耗

**非目标**：不上任务队列

**对后续 Stage 的影响**：命中率决定是否需要付费源；`/metrics` 是 Stage 5 告警依据

---

### Stage 4：单页报告

**状态**：规划中
**目标**：能粘贴 IP 出多源报告

**核心假设**：
- H4：并列展示比单个总分更有说服力

**范围**：
- 一个页面，一个输入框
- 路由 / 注册 / 地理 / 信誉 / 历史分区展示
- 每个字段标注来源
- **页面底部固定一句：本页不提供总分**
- 无登录、无付费、无 JS 渲染核心数据

**验收**：
- [ ] 报告渲染正确，源失败可见
- [ ] 无任何形式的合并评分
- [ ] 首屏 HTML 含完整数据（爬虫可见）
- [ ] 移动端可用

**对后续 Stage 的影响**：这个页面的截图就是传播素材，设计质量直接决定 Stage 7 的效果

---

### Stage 5：纯文本接口 + 上线

**状态**：规划中
**目标**：`curl <domain>/1.1.1.1` 可用；站点对公网可达

**范围**：
- 纯文本响应（Content-Type: text/plain）
- 单 VPS 部署：Caddy + Go 单二进制
- Cloudflare 前置：DNS / CDN / WAF / 限流
- 基础监控：源失败告警

**验收**：
- [ ] `curl` 返回可读文本
- [ ] 限流生效
- [ ] 源失败时页面与 curl 都如实反映
- [ ] 日志能看到调用了哪些源

**对后续 Stage 的影响**：MVP 到此为止。**是否继续做 Stage 6+，由 Stage 7 的反馈决定**

---

### Stage 6：ASN 页与历史时间序列

**状态**：规划中
**目标**：SEO 资产 + 唯一的护城河

**范围**：
- `/asn/<asn>` 静态页，聚合该 ASN 的统计
- 查询历史页：同一 IP 上次与本次的字段差异
- sitemap / robots.txt / llms.txt

**验收**：
- [ ] ASN 页有非模板化的聚合数据
- [ ] 历史差异展示正确
- [ ] 爬虫可抓，结构化数据合法

**已知局限**：历史数据量取决于上线后的真实查询量，早期会很稀疏

---

### Stage 7：对外发布与反馈回收

**状态**：规划中
**目标**：验证 H1（二次）与 H5

**范围**：
- 发布对外推广文章
- V2EX / 主机论坛 / Reddit（r/sysadmin, r/webhosting）
- 收集反馈：人们最在意哪个字段？有没有人问 API？

**验收**：
- [ ] 至少收到 10 条实质反馈
- [ ] 有真实用户发来自己的 IP 求对照
- [ ] 记录"用户最常看什么"用于后续优先级排序

**这是整个项目的转折点。** 反馈决定 Stage 8+ 是往"代理 IP 质量"走，还是往"历史数据服务"走，还是停在这里。
