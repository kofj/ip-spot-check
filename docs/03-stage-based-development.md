# 分阶段开发

**最后更新**：2026-10-31

## 概述

每个 Stage 是一个小而完整、可验证、可回滚的交付单元。

## Stage 生命周期

```
[GATE 0] 启动
    |
[GATE 1] 设计文档
    |
[GATE 2] 设计评审
    |
[GATE 3] 实现与测试
    |
[GATE 4] 代码评审
    |
[GATE 5] 完成检查
```

## Stage 规模规则

- **时长**：1–3 天
- **范围**：单一聚焦功能
- **假设**：1–3 个核心假设
- **产出**：可测试、可演示的东西

## 完成标准

- [ ] 验收标准全部满足
- [ ] 单元测试通过（覆盖率 >= 20%）
- [ ] E2E 验证关键路径
- [ ] 真实环境验证
- [ ] 设计文档与实现一致
- [ ] 技术债账本已更新
- [ ] ADR 已记录（含对后续 Stage 的影响）

## 回滚策略

每个 Stage 必须写明：
1. 回滚到哪个版本
2. 怎么回滚
3. 数据迁移影响（如有）

## 本项目特别约定

**每个 Stage 结束时，必须能回答：这个 Stage 验证了什么假设？**

因为项目的核心风险不是技术，而是「多源并列这件事到底有没有人需要」。每个 Stage 都应该带着这个验证前进，而不是单纯堆功能。

**Stage 顺序按风险从高到低排，而不是按依赖从底到顶排。** 先验证最可能被推翻的东西——否则会在错误的方向上把地基打得很牢。
