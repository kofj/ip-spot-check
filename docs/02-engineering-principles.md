# 工程原则

**最后更新**：2026-10-31

## 核心原则

### 1. 奥卡姆剃刀优先

不做没必要的事。这个项目的定位是"安全前提下好玩"，不是"完整的产品"。任何一个功能都要回答：**现在不做会怎样？** 如果答案是"没什么"，就不做。

已否决的方案在动手前要重新确认一遍，不要在同一个坑里踩两次。

### 2. 存原始观测，不存结论

每个源给什么就原样存什么。分数、判定、分类都在查询时计算。这样：
- 方法学可以公开、可复现
- 改权重不用重跑历史
- 用户能看到证据链而不是我们的主观判断

### 3. 多源并列，不合并

不出现"总分"。不出现"风险等级"。每个源独立展示、独立降级。

这不是 UI 偏好，是**产品定义的边界**：没有总分就卖不了"纯净 IP"，也就没有商家来围猎。

### 4. 源失败必须可见

某个数据源挂了，页面如实显示"该源暂不可用"，而不是显示旧值或空值。分数是拼出来的，一个源故障不能伪装成正常。

### 5. 措辞即法律

只转述源结论，不做主观定性。写「AbuseIPDB 报告 47 次」，不写「该 IP 是攻击者」。这条规则没有例外。

### 6. 先跑通再优化

MVP 不做队列、不做 Pages/VPS 拆分、不做全量索引。等出现真实痛点再做对应优化。过早拆分等于给自己造 CORS 和部署问题。

## 代码规范

- Go 标准风格，`gofmt` / `go vet` 必须过
- **非必要不加注释**，命名要能自解释
- 每个源一个 adapter，边界清晰、可替换
- 单元测试覆盖 >= 20%（MVP 阶段），关键路径必须测

## 审查规范

- 设计文档先审再实现
- 代码审关注：源降级是否正确、措辞是否越界、错误是否被吞
- 低置信度发现交人工确认

## 部署边界

**当前是单实例架构。** 不预付多副本的复杂度，但进程内状态必须走接口抽象、配额计数必须持久化——因为多副本时这些状态不会报错，只会静默变差。

详见 ADR-7 与 `docs/stages/stage-0.md` 的「单机部署边界」。

## 性能约束

- 查询 P95 < 2s（并行拉源）
- 24 小时缓存命中率 > 60%（这决定了免费额度能撑多大）
- 单次查询最多少消耗 N 次外部 API（由缓存策略控制）
